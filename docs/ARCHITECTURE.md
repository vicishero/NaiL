# NaiL (PaoPao) 后端架构文档

本文档描述NaiL项目的Go后端代码结构与架构设计。

---

## 🏗️ 整体架构层次
项目采用经典的**分层架构**设计，各层职责清晰，依赖关系明确：

```
┌─────────────────┐
│   接入层 (API)  │  auto/* + mirc/*  接口定义与路由绑定
├─────────────────┤
│   服务层 (Serv) │  internal/servants/*  业务逻辑处理
├─────────────────┤
│   核心层 (Core) │  internal/core/*  核心业务模型与接口定义
├─────────────────┤
│   数据层 (DAO)  │  internal/dao/*  数据库操作与缓存
├─────────────────┤
│   基础设施层    │  internal/infra/* + pkg/*  通用工具与中间件
└─────────────────┘
```

### 依赖原则
- 上层依赖下层，下层不依赖上层
- 各层依赖抽象接口，不依赖具体实现
- 核心层（Core）不依赖任何其他层，是整个项目的业务契约

## 📁 目录详解

### 项目根目录
```
/
├── auto/            # 自动生成的代码（API接口、路由绑定等）
├── cmd/             # 命令行入口（启动文件）
├── custom/          # 自定义数据目录（运行时生成的文件）
├── docker/          # Docker相关配置
├── docs/            # 项目文档
├── internal/        # 核心业务代码（Go内部包，不对外暴露）
├── mirc/            # Mir接口定义（API规范描述）
├── pkg/             # 公共工具包（可对外暴露的通用库）
├── proto/           # Protobuf协议定义
├── scripts/         # 部署、迁移等脚本
├── web/             # 前端Vue项目
├── main.go          # 项目主入口文件
└── go.mod           # Go模块依赖
```

---

### 1. 接口定义层 `auto/` & `mirc/`
#### `auto/` - 自动生成代码
```
auto/
├── api/             # 自动生成的API接口定义与路由绑定
│   ├── v1/          # v1版本普通用户API
│   └── m/           # 管理后台API
└── rpc/             # 自动生成的RPC接口
```
- 由Mir框架根据`mirc/`目录下的接口定义自动生成
- 包含请求参数绑定、路由注册、响应渲染等模板代码
- **禁止手动修改**，重新生成会被覆盖

#### `mirc/` - Mir接口定义
```
mirc/
├── admin/           # 管理员API定义
├── bot/             # 机器人API定义
├── localoss/        # 本地OSS服务API定义
├── space/           # 空间功能API定义
└── web/             # Web端用户API定义
```
- 使用Mir框架的DSL定义API接口规范
- 每个文件对应一个业务模块的接口定义
- 定义请求参数、响应格式、权限要求等
- 是前后端对接的唯一接口规范，修改需要同步前后端

---

### 2. 命令入口层 `cmd/`
```
cmd/
├── migrate/         # 数据库迁移命令
└── serve/           # 服务启动命令
```
- 遵循Go项目最佳实践，每个命令一个独立目录
- 主入口`main.go`会根据命令行参数调用对应cmd的入口函数
- 示例：
  - `./paopao serve` 启动Web服务
  - `./paopao migrate` 执行数据库迁移

---

### 3. 核心业务层 `internal/`
所有核心业务逻辑都在这个目录下，作为Go内部包，不对外暴露。

#### `internal/conf/` - 配置管理
```
conf/
├── config.yaml      # 默认配置文件模板
├── conf.go          # 配置结构定义
└── setting.go       # 系统配置相关常量
```
- 统一管理所有配置项
- 支持配置文件、环境变量、命令行参数多来源配置
- 提供类型安全的配置访问接口

#### `internal/core/` - 核心领域模型
```
core/
├── cs/              # 公共结构体、常量、枚举定义
├── ms/              # 业务模型层定义
└── *.go             # 核心业务接口定义
```
- 定义所有业务领域模型、接口、常量、枚举
- 不依赖其他任何层，是整个项目的核心业务契约
- 所有上层都依赖这一层的定义，实现业务与技术实现解耦

#### `internal/dao/` - 数据访问层
```
dao/
├── cache/           # 缓存操作封装（Redis等）
├── jinzhu/          # 数据库操作封装（GORM实现）
│   ├── dbr/         # 数据库表Model定义，与表结构一一对应
│   └── *.go         # 各个业务模块的DAO接口实现
└── index/           # 搜索引擎操作封装（MeiliSearch、Zinc等）
```
- 封装所有数据操作：关系型数据库、缓存、搜索引擎、对象存储等
- 对外提供统一的数据访问接口，屏蔽底层实现细节
- 实现了多级缓存策略，大幅提升系统性能

#### `internal/infra/` - 基础设施层
```
infra/
├── base/            # 基础组件封装
└── *client.go       # 第三方服务客户端封装
```
- 封装所有第三方服务的客户端：Redis、MySQL、OSS、搜索引擎、消息队列等
- 提供连接池管理、错误处理、监控埋点等公共能力
- 统一第三方服务的使用方式，便于替换实现

#### `internal/model/` - 数据模型层
```
model/
├── web/             # Web层请求/响应模型定义
└── *.go             # 通用模型定义
```
- 定义API层的请求参数和响应结构体
- 实现参数校验、格式转换、字段脱敏等逻辑
- 是前后端数据交互的契约，修改需要同步前后端

#### `internal/servants/` - 服务层/接口实现层
```
servants/
├── admin/           # 管理员接口实现
├── base/            # 基础服务抽象
├── web/             # Web端用户接口实现
│   ├── admin.go     # 管理员相关接口实现
│   ├── core.go      # 核心业务接口实现
│   ├── loose.go     # 宽松权限接口实现（不需要登录）
│   └── priv.go      # 需要登录的私有接口实现
└── chain/           # 中间件链定义
```
- **接口实现层**，实现`mirc/`中定义的所有API接口
- 处理具体的业务逻辑，调用DAO层获取数据、调用Core层处理业务规则
- 中间件链处理认证、鉴权、限流、日志、监控等横切关注点

#### `internal/sitesetting/` - 系统设置模块
```
sitesetting/
└── *.go             # 系统配置中心实现
```
- 实现动态系统配置功能
- 支持管理员后台修改配置，无需重启服务
- 处理配置的加密存储、版本管理、热加载等能力

### 4. 公共工具层 `pkg/`
```
pkg/
├── app/             # Web应用基础组件
├── convert/         # 类型转换工具
├── debug/           # 调试工具
├── http/            # HTTP客户端工具
├── json/            # JSON处理工具
├── naming/          # 命名规范工具（驼峰、下划线转换等）
├── types/           # 通用类型定义
├── utils/           # 通用工具函数
├── version/         # 版本信息管理
```

- 通用工具包，无业务逻辑，可以被其他项目引用
- 不依赖项目内部的业务代码
- 提供项目中常用的工具函数和通用能力

## 🔄 请求处理流程
```
客户端请求
    ↓
路由匹配（自动生成的路由）
    ↓
中间件链执行（JWT认证、权限校验、限流、日志、监控等）
    ↓
参数绑定与校验
    ↓
调用Servant层对应接口处理业务逻辑
    ↓
调用DAO层操作数据（数据库+缓存）
    ↓
组装响应数据
    ↓
返回给客户端
```

## ✨ 架构特点
1. **分层清晰**：各层职责单一，依赖关系明确，便于维护和扩展
2. **代码生成**：API接口自动生成，减少重复劳动，保证前后端接口一致性
3. **面向接口**：Core层定义抽象接口，各层依赖接口而非具体实现，易于单元测试和功能扩展
4. **配置中心**：支持动态配置，无需重启服务即可修改系统设置
5. **多存储支持**：支持多种数据库、缓存、对象存储、搜索引擎，易于替换底层实现
6. **易于部署**：编译为单二进制文件部署，支持Docker、K8s等多种部署方式
7. **性能优异**：内置多级缓存、连接池、异步处理等优化，支持高并发场景

---

## 📌 开发规范
1. 新增API接口先在`mirc/`目录下定义，执行`go generate`生成`auto/`代码
2. 业务逻辑尽量写在Servant层，避免在DAO层写业务逻辑
3. 核心业务规则定义在Core层，保证业务逻辑的一致性
4. 公共工具函数放到`pkg/`目录，不要在业务代码中重复实现
5. 数据库操作必须通过DAO层，禁止在业务代码中直接操作SQL
6. 所有错误都使用`pkg/xerror`中定义的错误类型，统一错误码和错误信息
